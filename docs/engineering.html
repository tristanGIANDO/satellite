Part III · Engineering

Anyone can run it once.

Part II ends with a checkpoint and an algorithm that work. Neither is worth much on its own: a scene is 450 MB, a month of them is fifteen scenes, and a year of one tile is roughly 80 GB for a result that saturates after four clear dates. This part is everything built around the model so that running it again — on another tile, another month, another grading — costs minutes instead of days.

01

Pipeline — what actually runs

A model that only exists inside a notebook is a demo. Everything that makes it usable is around it.

There is no cluster here and no scheduler: it is a single CPU process you point at a tile and a date range. But a run reads hundreds of gigabytes and takes about twenty minutes per month, which forces exactly the properties an ML pipeline needs anyway. Every stage is idempotent, every stage is resumable, every stage is skippable when its output already exists, and each run leaves the metrics it should be judged on behind it.

Four properties, and what each one bought

  1. Decide before you download. A single date is ~450 MB and a month holds fifteen of them; a year of one tile would be roughly 80 GB for a result that saturates after four clear dates. So every candidate date is scored while it is still on the server: JPEG2000 stores reduced-resolution copies inside the file, GDAL fetches only those bytes over HTTP range requests, and a scene is ranked from a 915-pixel sample of its blue and cirrus bands. Only the cleanest few are ever pulled. This is the single decision that turned "a year of imagery" from impractical into an overnight batch.
  2. Idempotent ingest. Downloads skip anything already on disk, missing acquisitions 404 and are logged, and the layout is addressed by what the file is: sentinel2/<date>/<tile>/B04.jp2. Re-running a month costs a directory listing. The batch loop skips whole months whose export already exists, so an interrupted year resumes at the month it died on.
  3. Resumable state, and a checkpoint that outlives its run. The mosaic persists as RGBA where alpha marks the pixels already holding real ground, keyed by tile and month. A run that dies at date 9 of 14 restarts with most of the work intact. Better: because the checkpoint holds the composited result, the grading is separable — white point and contrast can be changed and reviewed across a whole year in seconds per month, instead of the ~20 minutes a month costs to rebuild. Presentation stopped being coupled to computation, which is what made the twelve-month series tunable at all.
  4. Metrics as a first-class output. Every date logs what it contributed: usable fraction, newly filled, improved, cumulative coverage, and the overlap in pixels used for the radiometric fit. Fig. 16 in Part II is plotted directly from that log, and the per-date masks in output/masks/ are its visual counterpart. When a run degrades, both the number and the picture that explains it are already on disk.

Quality gates

Everything checkable before a commit is checked: ruff with an explicit rule set (pycodestyle, pyflakes, bugbear, isort, pyupgrade, annotations, google-style pydocstyle, plus a debugger and print ban), a large-file guard so no 250 MB export is ever committed, commitizen for conventional commits, prettier on Markdown. CI publishes this documentation on every push to main. Failures inside the year batch are caught per month and logged with a traceback, so one bad month never takes the other eleven with it.

Honest gaps

Training still lives in a notebook, so a run is reproducible only by hand; the model registry is a filename convention (simple_unet_v2_subset4000_epoch20.pth) and the checkpoint is pinned as a literal path in the entrypoint. No experiment tracker, no data versioning, no test suite, and inference_pipeline.log is opened with mode="w" — each run erases the previous run's metrics, which is exactly the file I keep wanting to compare against. The next step is not a better model: it is a training script with hyper-parameters as arguments, metrics written next to the checkpoint, and a one-tile smoke test in CI.

02

Profiling — where the time and the memory actually went

One date took 4 minutes 47 and peaked at 11.7 GB of RAM. Three quarters of that time was the model, and almost all of the rest ran on a single core out of sixteen. Fixing the six things below took the same two-date run from 451 s and 22.5 GB to 262 s and 10.1 GB — 1.7× the speed on 45% of the memory, with the mosaic unchanged.

Measured, not estimated, before and after: every stage of a real scene — tile 31UDQ, 13 June 2025, 10 980 × 10 980 px — instrumented with wall time, peak resident memory and process CPU sampled every 100 ms.

Bottleneck 1 — inference, was 72% of the run

1 764 tiles went through the network one at a time, at 625% CPU on a machine that offers 1600%. Three changes, in ascending order of surprise. The forward pass ran without torch.no_grad(), so autograd built and kept a graph for every one of those tiles that was never differentiated; inference_mode alone is worth 1.4×. Batching 16 tiles per forward instead of 1 brings it to 1.7× — 8, 32 and 64 all measured slower, so 16 is the setting rather than a round number. And torch's default thread count is one per physical core, the usual advice for bandwidth-bound convolution, which is simply wrong here: 8 threads gives 59 ms per tile, 12 gives 47 and 16 gives 48. A 256 px tile is small enough that much of each pass is latency rather than saturated arithmetic, and the second thread on a core fills it. Together: 82.7 ms per tile down to 39.5, at 1456% CPU instead of 772%.

Bottleneck 2 — was 66 seconds on one core

preprocess, cloud_pixel_mask and _align_to_mosaic were 23% of the run and each pinned exactly one core. Two of them were doing far more arithmetic than their own output justified: the contrast stretch called np.percentile on 120 Mpx per channel — sorting the entire scene to recover two numbers — and the radiometric fit reduced a gigabyte-scale masked copy to four scalars. Measured on every 4th pixel of each axis, those statistics agree to 0.1% for a sixteenth of the work: 25.8 s → 4.1 s and 19.1 s → 2.2 s.

The distance transform was the interesting one. SciPy's EDT is single-threaded and returns float64 — a 964 MB array — and only two thresholds are ever read from it, 100 px for dilation and 300 px for the shadow search. So it now runs on a 4×-downsampled grid and only the thresholded booleans are expanded back, which means the float64 distance field never exists at scene resolution. Blocks are OR-pooled and the threshold carries one block of slack, so the approximation can only ever mask more than the exact transform, never less — the direction that costs a few pixels a later date refills, rather than the one that leaks cloud into the mosaic. On this scene: zero under-masked pixels, 0.21% over-masked, 21.3 s → 6.2 s.

Bottleneck 3 — memory that only grew

Peak resident memory was 11.7 GB for a 964 MB scene, and it climbed monotonically because nothing was released between stages. Four things were holding it up. The whole-scene float32 twin was pointless — the model consumes 256 px tiles, so the cast belongs inside the tile loop, which deletes a 1.93 GB allocation outright. The per-date cloud masks were kept as float32 RGB purely to be written out as grayscale previews, growing the run by 1.4 GB per date; one uint8 channel is 12× smaller and produces the same PNG. And each stage now drops its arrays before the next allocates, so peak tracks the working set rather than the whole run.

The fourth was hiding in plain sight: np.percentile returns np.float64 scalars, and NumPy promotes on those rather than treating them as weak. Subtracting one from the float32 mosaic silently returned a float64 array — the final image, and the largest allocation in the pipeline, was quietly double width for want of a float(). Over two dates: 22.5 GB down to 10.1 GB.

GPU — absent by construction

The installed wheel is torch 2.7.0+cpu: there is no CUDA runtime in this environment, so the GPU is not underused, it is unreachable. That is a defensible choice for a pipeline whose unit of work is a 450 MB download, and it is why the fixes above mattered — they were worth roughly the same as moving to a GPU while changing nothing about the deployment.

What is left

  1. Decoding is now the floor. load_and_stack is unchanged at 10.5 s and has gone from 4% of the run to 9%. It already runs at 1071% CPU, so what is left there is the disk and the JPEG2000 codec, not the code.
  2. remove_small_objects is what remains of the cloud mask. Of the 6.2 s that stage still costs, most is now connected-component labelling over 120 Mpx, single-threaded, with an integer label array to match. Coarsening that too would change what min_cloud_size means, so it is left alone deliberately.
  3. The three NumPy stages still pin one core. They are 12 s rather than 66, so the remaining prize is small — but nothing here was parallelised across cores, only made to do less work.

Caveat, stated because it changes how these numbers should be read: the original measurement ran with a second inference job on the machine, so the per-stage "before" wall times are pessimistic by an unknown margin. The before/after totals quoted at the top — 451 s → 262 s and 22.5 GB → 10.1 GB — come from running the old and the new code back to back over the same two dates on an otherwise idle machine, and are the ones to trust. Both runs produce the same mosaic: the same white-point gains to three decimals, and 95.90% of the scene filled against 95.89%.

03

Architecture — onion, and where it paid

The compositor does not know it is reading JPEG2000. That is the entire point of the layout.

The code is onion-shaped: domain at the centre, application around it, infrastructure outside, and scripts as the only entrypoints. Dependencies point inward only. The domain imports NumPy, SciPy and scikit-image and nothing of ours. The application holds the algorithm — the compositing loop, the contamination score, the radiometric alignment, the grading — and declares abstract ports for anything it cannot do itself. Infrastructure implements those ports, and is the only place that has heard of rasterio, torch, S3 or PNG.

What each layer is allowed to know

LayerHoldsMay import
domain/ Tile, TileGrid, ImagePaths, cloud_pixel_mask, checkpoint splitting NumPy, SciPy, scikit-image — nothing of ours
application/ run_inference_pipeline, contamination score, radiometric alignment, grade_mosaic, the two ports domain/ only
infrastructure/ rasterio JP2 reader, torch U-Net, mosaic store, S3 listing and download domain/ and the ports
scripts/ entrypoints: choose tile, dates and checkpoint, wire the concrete adapters everything
Finding

The layering paid for itself three times, always the same way. Going from tile-level to per-pixel selection rewrote run_inference_pipeline and touched not one line of the JP2 reader, the model service or the store. Adding the cirrus veto added one method to a port and one implementation. And re-grading a whole year was possible only because the composited mosaic is a domain object in a store, not a JPEG somewhere: a new script reads the checkpoints, calls an application function, and writes through the same adapter. When the algorithm is the thing you are iterating on, keeping I/O out of it is what makes the iteration cheap.

Where it leaks

estimate_contamination and its remote twin exist on JP2StackedImage but were never declared on StackedImageService, so the entrypoint that ranks dates is talking to a concrete adapter rather than a port — and main() constructs that adapter itself instead of receiving it. Both are two-line fixes and both are the classic way an onion erodes: not by a bad decision, but by a useful method added where it was easiest to write.

The cost is real: five files to add one band, and an abstract service with exactly one implementation. That is over-engineering right up until the second implementation appears — and here the second implementation is the next satellite. Landsat, SPOT, anything with four bands and a grid: the pipeline above it would not change.

Colophon

Python, PyTorch, rasterio, NumPy, scikit-image, SciPy. Hexagonal layout — domain, application, infrastructure — so the compositor never knows it is reading JPEG2000. Inference runs on CPU: about three minutes per date, so under an hour for a full month of the Paris tile, and it checkpoints as it goes — the mosaic is stored as RGBA, alpha marking which pixels are already settled, so a later run only pays for the holes.

That checkpoint is also what made the grading tractable. It holds the composited result, so the white point and the contrast can be changed and judged across all twelve months in a few minutes, instead of the three hours it takes to rebuild them. Every grading decision on this page was made that way.

Figures on this page are downscaled. Full-resolution outputs are 10 980 px square and 200–280 MB each.
